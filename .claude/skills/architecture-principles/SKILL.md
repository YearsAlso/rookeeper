# Architecture Principles — 架构设计原则

设计代码架构时必须遵循的原则体系。**硬性约束不可违反**；**必备能力是每次架构设计必须执行的动作**；**输出规则是违规时必须的反馈形式**。

## 使用场景

- **software-engineer**：设计/编写代码架构时强制遵循（设计先行于编码）
- **reviewer**：architecture-review 审查时校验硬性约束，发现违规按输出规则告警
- **architecture-reasoning**：推演出的设计方案必须满足本 skill 的硬性约束

## 硬性约束（不可违反）

### 1. Crate 依赖方向

- 依赖方向：**protocol 无依赖 → storage 依赖 protocol → platform 无依赖 → client/server 依赖 protocol+platform → cli 依赖全部**，依赖仅允许单向
- 核心业务 crate（`protocol`）禁止直接依赖框架/外部服务
- 跨 crate 交互必须使用公开类型（通过 `pub use` 导出），禁止间接依赖
- 违反判断：`protocol` 中出现 `rookeeper-storage` 引用 → 🔴 阻断；`storage` 中出现 `rookeeper-client` 引用 → 🔴 阻断

### 2. Trait 抽象隔离

- 外部依赖（序列化、存储后端、传输层）必须用 trait 抽象，业务代码不能绑定具体技术
- 替换外部依赖（换序列化格式/换存储后端/换传输方式）只允许修改抽象层，不允许波及业务代码
- 违反判断：业务 crate 直接使用第三方类型作为方法签名/字段类型（未经过 trait 抽象）→ 🔴 阻断

### 3. 重构纪律

- 重构不改动外部行为（接口契约、响应格式、存储结构语义不变）
- **无测试不做大重构**；小步迭代，每步可编译、可测试
- 重构与新功能代码**分开提交**，禁止混在一次提交中
- 违反判断：重构变更了对外契约或与功能代码同提交 → 🔴 阻断

### 4. 代码质量底线

- 杜绝：重复代码（DRY）、巨模块（>400 行）/长函数（>60 行）、魔法数字、模糊命名
- 新增代码必须达到：命名自解释、单一职责、复杂度可读
- 违反判断：明显重复实现/超长方法/裸数字/含义不明的命名 → 🟡 警告（巨模块长函数可升 🔴）

### 5. 渐进改造

- 优先渐进改造，不轻易全盘重写（重写 = 高风险，必须走 architecture-reasoning 推演 + 明确理由）
- 临时妥协（如硬编码、跳过重构、临时结构）必须标记技术债务：位置 + 原因 + 偿还时机
- 违反判断：大范围重写无推演记录 / 临时妥协无技术债标记 → 🔴 阻断

### 6. 开闭原则

- 稳定模块不依赖易变模块；对扩展开放、对修改封闭
- 新增需求优先走"扩展"（新 trait 实现/新适配器），不走"修改稳定代码"
- 违反判断：为新增需求修改已稳定模块的核心逻辑（可扩展而未扩展）→ 🟡 警告（影响大升 🔴）

## 必备能力（每次架构设计必须执行）

| 能力 | 动作 | 执行时机 |
|------|------|---------|
| 非法依赖自动校验 | 检查新增依赖方向（protocol 是否引用其他 crate、跨层直引） | 编码前设计完成时 |
| crate 越界检测 | 检查模块职责是否越界（如 protocol 中写存储逻辑、storage 中写协议解析） | 编码前设计完成时 |
| 坏味道识别与重构方案 | 识别重复代码/巨模块长函数/魔法数字/模糊命名/过度耦合，给出可落地的重构方案 | 设计评审与审查时 |
| 防腐抽象设计 | 对外部依赖（第三方 crate/外部系统）主动设计 trait 抽象层，业务侧只见接口 | 引入新依赖时 |
| 依赖风险评估 | 改动前评估：变更影响面、被依赖方稳定性、替换成本、升级风险 | 任何架构/依赖变更前 |
| 业务与存储/网络隔离 | 业务逻辑（protocol 中的模型）不感知文件 I/O/网络传输细节，全部经 trait 委托 | 编码前设计完成时 |

## 输出规则

- 发现违规架构、代码问题时**主动告警**，不得沉默通过
- 告警格式：`文件:行号` + 违反的约束编号（如"约束 2 Trait 抽象隔离"）+ 严重级别 + **可落地的修改方案**（具体到改哪个 crate/加哪个 trait/如何调整依赖）
- 严重级别沿用统一分级：🔴 阻断（必须修复）/ 🟡 警告（建议修复）/ 🔵 建议（可选）

## 与相关 skill 的关系

- **architecture-review**：按本 skill 的硬性约束作为审查维度执行
- **architecture-reasoning**：推演设计时以本 skill 为约束底线；冲突时优先本 skill
- **architect-memory**：本 skill 红线被违反并修复后，由 reviewer 记录教训到架构记忆
