# SDD 规范驱动开发约束

## 原则

**任何非平凡变更（影响 > 1 个文件，或涉及架构决策，或变更业务逻辑）必须走 SDD 流程：先出规范，再编码。**

本规则与 `ask-dont-assume.md` 互补：ask-dont-assume 管"不脑补需求"，本规则管"变更的流程纪律"。

## SDD 工作流

```
Spec-First → Design → Implement → Verify → Archive
```

| 阶段 | 操作 | 产出 |
|------|------|------|
| 1. Spec | 编写/更新 `specs/` 下的规范文档 | `specs/<name>/spec.md` |
| 2. Design | 基于 spec 编写技术设计 | `specs/<name>/design.md` |
| 3. Implement | 按设计实现代码 | 代码变更 |
| 4. Verify | 验证实现与 spec/design 一致 | 验证报告 |
| 5. Archive | 关闭变更，归档到 `docs/` | 更新 `docs/` |

## 触发条件

以下情况**必须**走 SDD 流程：

- 新增功能 / 模块 / API 端点
- 修改数据库表结构或枚举类型
- 修改哈希链计算逻辑或 WORM 写入策略
- 修改接口契约（请求/响应结构、路由路径、认证方式）
- 引入新的依赖或第三方库
- 重构超过 2 个文件
- 变更影响 FDA 21 CFR Part 11 合规路径

以下情况**可以**跳过 SDD 流程：

- 单文件 bug 修复（改 < 20 行，逻辑不变）
- 注释 / 文档更新
- 纯配置变更（config/rookeeper.default.toml 或 Cargo.toml）
- 测试代码变更

## Spec 内容要求

每个 Spec 必须包含：

- **业务背景**：为什么要做这个变更
- **功能范围**：包含和不包含的功能边界
- **接口契约**：API 路径、请求/响应结构、状态码
- **数据模型**：新增/修改的表、字段、索引
- **合规影响**：是否影响 FDA 21 CFR Part 11 合规路径
- **边界条件**：异常场景、错误处理、幂等性

## 文档一致性要求

1. 实现完成后，必须运行 `pm` agent 进行文档比对审核
2. 审核确认 `docs/` 中的技术文档与代码实现一致
3. 如果文档与代码存在差异，必须先更新文档再合入代码
4. `docs/` 是可信源，代码变更必须与文档描述一致

## 禁止行为

- ❌ 非平凡变更不走 SDD 流程
- ❌ 实现完成后不更新 `docs/` 相关文档
- ❌ 代码与 `docs/` 文档描述不一致时合入代码
