## 1. 产品愿景重新定义

### 1.1 Firebase 核心价值在工控场景的映射

Firebase 的三大核心价值在工业场景的落地分析：

| Firebase 核心能力 | 消费互联网场景 | 工业场景落地映射 |
|---|---|---|
| **实时同步（Realtime Sync）** | 多端数据实时更新、在线协作 | 同一产线上多设备（PLC、传感器、HMI）状态实时共享；多客户端（监控大屏、移动终端）同步刷新 |
| **离线优先（Offline-First）** | 网络不稳定时的本地缓存与自动同步 | 工厂车间网络频繁中断；设备离线时本地记录数据、命令队列缓存，恢复后自动上报/补发 |
| **简单接入（Simple Integration）** | SDK 五行代码接入，多平台支持 | 工业设备（PLC/嵌入式）资源受限；需要轻量级协议（MQTT/CoAP/WebSocket）、多语言 SDK、最小化依赖 |

### 1.2 产品愿景陈述

**一句话愿景：**

> 为工业单机节点提供"本地优先、数据协同、接入简单"的实时数据协调能力，让任何工业设备无需云端即可实现多组件间的状态同步与命令下发。

**延伸定义：**

- **本地优先（Local-First）**：数据主权归节点所有，不依赖外部云服务；即使网络中断，本地业务不降级
- **数据协同（Coordination）**：多个进程/设备读写同一份共享状态，带冲突解决机制
- **接入简单（Simple Integration）**：提供工业友好的协议接口（MQTT、HTTP/WS），客户端 SDK 最小化

### 1.3 关键约束

- **单机部署**：不依赖分布式集群，所有能力运行在单一节点（可嵌入到工业网关、边缘控制器）
- **工业级可靠性**：要求数据持久化、进程崩溃恢复、不丢命令
- **资源约束友好**：支持低至 256MB RAM 的嵌入式设备

## 2. 目标客户与痛点分析

### 2.1 目标客户画像

| 客户类型 | 典型角色 | 描述 |
|---|---|---|
| **设备商（OEM）** | 设备研发工程师 | 生产 PLC、传感器、网关等硬件设备，需要设备间协同能力 |
| **集成商（SI）** | 系统集成项目经理 | 将不同厂商设备集成到统一产线，需要统一的数据协调层 |
| **终端工厂（End User）** | 产线运维工程师 | 运行已有设备系统，需要实时监控、故障告警、远程控制 |

### 2.2 核心痛点

#### 设备商痛点

| 痛点 | 描述 | 严重程度 |
|---|---|---|
| **设备孤岛** | 设备间缺乏标准数据交换机制，厂商自家设备能通信，跨厂商就无法协同 | 高 |
| **协议碎片化** | Modbus、OPC UA、MQTT、Profinet 等协议不统一，每接一个新设备需要重新开发驱动 | 高 |
| **无状态困境** | 设备重启后状态丢失，业务逻辑不得不依赖外部数据库来维护状态 | 中 |
| **固件更新难** | 现场设备无法远程批量更新，需要工程师到场操作 | 中 |

#### 集成商痛点

| 痛点 | 描述 | 严重程度 |
|---|---|---|
| **数据聚合复杂** | 需要将多个设备的数据统一格式后供上层系统使用，现有方案需要写大量粘合代码 | 高 |
| **命令下发不可靠** | 下发命令到设备后无法确认是否送达、是否执行；重发策略需要自己实现 | 高 |
| **调试困难** | 现场问题难以复现，设备状态不透明，缺乏统一日志和追溯 | 中 |
| **扩展性差** | 添加新设备或新客户端需要修改核心逻辑，风险高 | 中 |

#### 终端工厂痛点

| 痛点 | 描述 | 严重程度 |
|---|---|---|
| **网络不稳定** | 车间网络频繁掉线，云端方案在断网时完全失效 | 高 |
| **数据丢失** | 网络中断期间的生产数据、报警记录丢失，无法补录 | 高 |
| **响应延迟** | 需要实时看到设备状态（秒级），现有方案 polling 延迟高 | 中 |
| **运维复杂** | 需要专门的 IT 人员维护数据库、中间件，学习成本高 | 中 |

## 3. 竞品分析

### 3.1 竞品对比矩阵

| 维度 | **Firebase RTDB** | **Firebase Firestore** | **本地文件** | **Redis** | **ZooKeeper** |
|---|---|---|---|---|---|
| **部署模式** | SaaS（必须联网） | SaaS（必须联网） | 单机本地 | 单机/集群 | 集群为主 |
| **离线支持** | ✅ SDK 自动缓存离线操作 | ✅ SDK 自动缓存离线操作 | ❌ 自行实现 | ❌ 需自行实现 | ❌ 无离线概念 |
| **实时同步** | ✅ WebSocket 长连接 | ✅ WebSocket 长连接 | ❌ 轮询或自己实现 | ❌ Pub/Sub 但非持久化 | ❌ 非为实时同步设计 |
| **数据持久化** | ✅ 云端持久化 | ✅ 云端持久化 | ✅ 本地文件 | ✅ RDB/AOF | ✅ 事务日志 |
| **冲突解决** | ✅ Last-write-wins + 自定义 | ✅ 乐观并发 | ❌ 无 | ❌ 无内置 | ❌ 无 |
| **协议适配** | JSON over WebSocket | JSON over WebSocket | 文件系统 API | Redis Protocol | ZAB 协议（Java） |
| **工业协议支持** | ❌ 无 | ❌ 无 | ❌ 无 | ❌ 无 | ❌ 无 |
| **轻量化** | ❌ 需云端依赖，SDK 较大 | ❌ 需云端依赖，SDK 较大 | ✅ 极轻量 | ⚠️ 中等（~10MB+） | ❌ 重（Java JVM） |
| **嵌入式友好** | ❌ | ❌ | ✅ | ⚠️ 可嵌入式（RedisModule） | ❌ |
| **命令可靠性** | ✅ 离线操作队列自动重试 | ✅ 离线操作队列自动重试 | ❌ 无 | ⚠️ 需 LPOP 实现队列 | ✅ 原子操作 |
| **工控场景适合度** | ❌ 不满足（云依赖） | ❌ 不满足（云依赖） | ❌ 不满足（无实时同步） | ⚠️ 可用但非最佳 | ❌ 架构过重 |

### 3.2 竞品核心局限总结

| 竞品 | 在工控场景的核心局限 |
|---|---|
| **Firebase RTDB/Firestore** | **强制云端依赖**——断网即失效；数据出墙问题（工业数据敏感）；无法私有化部署 |
| **本地文件** | **无实时能力**——需要轮询或 inotify；无并发控制；无冲突解决；无客户端感知 |
| **Redis** | **非为协同设计**——pub/sub 消息不持久化；没有离线操作队列；没有冲突解决；协议偏薄 |
| **ZooKeeper** | **架构过重**——需要 JVM；强一致性协议不适合低延迟场景；没有离线概念；学习曲线陡峭 |

### 3.3 差异化机会

**本产品的差异化定位：**

1. **本地优先 + 云无关**：不依赖任何外部服务，真正在边缘节点运行
2. **工业协议桥接**：原生支持 MQTT、CoAP、HTTP/WS 等工业友好协议
3. **离线操作队列**：类似 Firebase 的离线能力，但运行在本地
4. **嵌入式友好**：可编译为静态二进制，嵌入到工业网关（~20MB 总包）
5. **开箱即用的协同**：内置发布/订阅、持久化、冲突解决，无需业务代码二次开发

## 4. 用户场景优先级

### 4.1 P0 场景（MVP 必须覆盖）

> **定义：** 用户明确表示"如果这个能力没有，我完全不会考虑这个产品"的场景

#### P0-1：设备状态共享

**场景描述：** 同一产线的 PLC 和 HMI 需要共享当前生产状态（运行/停止/报警）。

**用户故事：**
> 作为 PLC 工程师，我希望 PLC 写入的状态能立即被 HMI 读取到，这样操作员不需要额外配置就能看到生产线状态。

**技术要求：**
- 键值对读写，支持 glob pattern 订阅
- 写入延迟 < 50ms（同节点进程间）
- 支持至少 100 个并发订阅者

#### P0-2：离线命令下发与确认

**场景描述：** 工程师从远程客户端下发控制命令给网关下的设备，网络中断后命令不丢失，恢复后自动送达。

**用户故事：**
> 作为运维工程师，我希望下发命令后，如果网络断开了，恢复后设备仍然能收到命令，我不想手动检查和重发。

**技术要求：**
- 命令持久化到磁盘（WAL）
- 离线期间命令队列化
- 送达确认（acknowledgement）机制
- 至少一次（at-least-once）投递保证

#### P0-3：简单 SDK 接入

**场景描述：** 嵌入式 C 程序通过 MQTT 接入协调服务，Python 脚本通过 HTTP 接入。

**用户故事：**
> 作为设备商工程师，我希望用最少的代码（< 20 行）让设备数据上报到协调服务，不需要学习复杂的中间件配置。

**技术要求：**
- 提供 MQTT 客户端兼容接口（publish/subscribe）
- 提供 HTTP REST 接口（GET/PUT/DELETE）
- 提供 Python SDK（pip install 即可）
- 提供 C SDK（静态链接）
- 零外部依赖（无 JVM、无 node_modules 运行时）

### 4.2 P1 场景（v1.0 后续迭代覆盖）

> **定义：** 增强型场景，有 P0 能力时可以工作，但没有时用户会找替代方案

#### P1-1：历史数据查询

**场景描述：** 运维人员需要查看过去 24 小时某设备的状态变化曲线。

**技术要求：**
- 内置时序数据存储（SQLite/LevelDB）
- 时间范围查询 API
- 数据保留策略可配置

#### P1-2：多节点数据汇聚（网关级联）

**场景描述：** 多个产线网关的数据需要汇聚到工厂级总网关。

**技术要求：**
- 节点间数据复制（ eventual consistency）
- 冲突解决策略可配置
- 带宽压缩传输

#### P1-3：告警规则引擎

**场景描述：** 当某传感器值超过阈值时，自动触发告警并推送。

**技术要求：**
- 规则 DSL（Domain Specific Language）
- 阈值比较、趋势检测
- 告警回调（webhook/邮件）

## 5. MVP 定义

### 5.1 MVP 能力集

**MVP 名称建议：** `industrial-sync` 或 `node-coord`

#### 核心能力（必须全部实现）

| 能力 | 描述 | 验收标准 |
|---|---|---|
| **KV 数据存储** | 键值对读写，支持 JSON 值 | 可存储/读取任意 JSON；支持 string/int/float/bool 类型 |
| **发布/订阅** | 基于 topic 的 pub/sub，wildcard 订阅 | `device/+/status` 可匹配所有设备；消息不持久化（纯内存） |
| **离线操作队列** | 网络断开时写入操作本地队列，恢复后自动重放 | 离线操作在恢复后 5 秒内重放完成 |
| **命令下发（带 ACK）** | 客户端下发命令，等待服务端确认 | 命令送达后返回 ACK；超时时间可配置（默认 10s） |
| **数据持久化** | 所有数据写入 WAL + 定期快照 | 进程 crash 后数据不丢；启动时自动恢复 |
| **MQTT 协议桥接** | 接入标准 MQTT 客户端 | 支持 MQTT 3.1.1；QoS 0/1 支持 |
| **HTTP REST 接口** | GET/PUT/DELETE 数据，WebSocket 订阅 | curl 即可测试；WebSocket 推送实时更新 |
| **进程管理** | systemd/launchd 服务化 | `systemctl start industrial-sync` 即可运行 |
| **配置管理** | YAML 配置文件 | 所有参数可配置；无硬编码 |

#### 技术约束（必须满足）

| 约束 | 标准 |
|---|---|
| **部署形态** | 单二进制文件（无 JVM、无运行时依赖） |
| **内存占用** | 空闲时 < 50MB RSS |
| **启动时间** | < 3 秒冷启动 |
| **磁盘占用** | 二进制 < 30MB |
| **可移植性** | Linux（x86_64, arm64）、macOS（x86_64, arm64）、Windows |

### 5.2 MVP 不包含（明确排除）

以下能力在 MVP 中**不会**提供，避免范围蔓延：

- ❌ 集群部署（多节点协同）
- ❌ 用户认证/权限管理（无安全层）
- ❌ 数据分析/聚合查询（纯 KV 操作）
- ❌ OTA 固件更新
- ❌ OPC UA / Modbus 协议桥接（仅 MQTT/HTTP）
- ❌ 容器化部署（直接二进制）

### 5.3 命名建议

| 候选名称 | 描述 |
|---|---|
| `industrial-sync` | 强调"同步"能力 |
| `node-coord` | 强调"节点协调"能力 |
| `edgefire` | Firebase 感，取"边缘版 Firebase"之意 |
| `localfire` | Firebase 感，取"本地版 Firebase"之意 |

**推荐：** `industrial-sync` ——明确表达工业用途，且与用户意图"单机 Firebase"呼应。

## 6. 附录

### 6.1 术语表

| 术语 | 定义 |
|---|---|
| **节点（Node）** | 部署本服务的一台物理机/虚拟机/嵌入式设备 |
| **客户端（Client）** | 连接到本服务的设备、脚本、应用程序 |
| **Topic** | 发布/订阅的主题路径，如 `line-1/plc-1/status` |
| **ACK** | Acknowledgement，命令送达确认 |
| **WAL** | Write-Ahead Log，预写日志，用于持久化 |
| **Offline Queue** | 离线操作队列，暂存网络断开期间的操作 |
