# rookeeper Phase 0 架构基线

## 1. 目标

Phase 0 的目标是先固定工程边界，而不是直接实现业务能力。所有后续功能都应建立在本文件定义的模块职责之上。

## 2. 模块划分

| 模块 | 职责 | 当前状态 |
| --- | --- | --- |
| `rookeeper-protocol` | 路径模型、节点元数据、ACL、错误码、二进制协议头、配置模型 | 已建立 |
| `rookeeper-storage` | 数据目录布局、WAL/快照路径规则、校验辅助 | 已建立 |
| `rookeeper-platform` | Linux / Windows 差异封装、默认 IPC 选择、服务资产命名 | 已建立 |
| `rookeeper-client` | 客户端配置与协议请求装配骨架 | 已建立 |
| `rookeeper-server` | 服务端启动入口、配置加载、基线运行摘要 | 已建立 |
| `rookeeper-cli` | 现场命令入口与运维辅助骨架 | 已建立 |

## 3. 逻辑分层

### 3.1 状态机层

负责命令解释、版本语义、节点生命周期和未来的 Watch 事件生成。该层必须是确定性的，不依赖随机数或墙上时钟决定业务结果。

### 3.2 存储层

负责 WAL、快照、目录布局、校验与恢复入口。Phase 0 先固化路径与文件命名规则，后续阶段再补具体读写实现。

### 3.3 传输层

负责本地 IPC 与二进制协议帧收发。Linux 优先 Unix Domain Socket，Windows 优先 Named Pipe，保留本地 TCP 兜底。

### 3.4 会话层

负责客户端连接、临时节点生命周期、未来锁与服务发现的会话归属关系。

### 3.5 Watch 分发层

负责订阅关系、事件排序、慢消费者背压隔离。Phase 0 只固定事件结构和边界，不实现行为。

## 4. 核心设计原则

1. **状态机纯净**：业务结果只由命令输入决定。
1. **平台差异下沉**：平台相关逻辑只能出现在 `rookeeper-platform` 及部署资产中。
1. **协议先行**：请求类型、错误码、配置字段在 Phase 0 就应稳定下来。
1. **轻量优先**：基线只引入首版真正需要的依赖。

## 5. 后续阶段挂接点

1. Phase 1 在 `protocol` 的模型之上补树形 KV、ACL 检查与 WAL/快照实现。
1. Phase 2 在 `protocol` 的事件与会话模型之上补 Watch、锁和服务发现。
1. Phase 3 在 `platform` 和 `server` 上补完整 IPC、服务管理、日志和指标。
